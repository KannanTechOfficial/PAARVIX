# Stage 1: Data Connectors (Excel, Google Sheets, MySQL)

Status: awaiting founder review. Date: 2026-11-01.

## Purpose

Paarvix becomes an ERP analytics platform for real companies and institutions. It reads the data they already have and stays read-only. It does not become an accounting system of record.

Stage 1 lets an admin connect the three most common sources and query them through one safe path. Later stages (dashboard builder, ERP template pack, alerts and roles, ERP connectors and AI) build on this.

**Success:** an admin uploads an `.xlsx`, links a Google Sheet, or connects MySQL, sees its tables and columns, and an Editor gets correct rows through `QuerySpec`. Nothing bypasses the role check or `SecurityContext`.

## Deployment model

Each institution or company runs its own Paarvix instance on its own server. One instance is one organisation. Multi-tenant cloud is P3, so stage 1 has no tenant isolation. `SecurityContext.tenantId` exists and is `null`.

## Sector neutrality

Paarvix serves colleges, hospitals, retailers, factories, government bodies and general companies from one codebase. The core knows nothing about any sector. No connector, query or API code may mention students, invoices, patients or similar. Sector knowledge lives only in template packs (stage 3), which declare the fields they need and are mapped to each customer's own columns.

`apps/api/src/college/` breaks this rule today, with hardcoded tables and routes. Stage 1 leaves it working. Stage 3 replaces it with the Education pack.

## Decisions

- Excel and Sheets data is imported into PostgreSQL. MySQL and PostgreSQL sources are queried live.
- Imported tables live in a dedicated schema, `paarvix_data`.
- Imported tables are reachable only through `QuerySpec`. Raw SQL is never allowed on them, because they share a database with application tables such as `users`.
- New dependencies: `exceljs` (MIT) and `mysql2` (MIT). Google access uses `fetch` and Node `crypto`, with no Google library.
- Automated tests are written for the `QuerySpec` compiler, read-only enforcement and import type inference. Other code is verified by compile and start, per the founder's preference.

## Architecture

### Connector contract

New folder `apps/api/src/datasources/connectors/`, one file per source type. Shared types go in `packages/shared/src/query.ts`.

```ts
interface SecurityContext {
  userId: string;
  role: 'ADMIN' | 'EDITOR' | 'VIEWER';
  tenantId: string | null;
  rowFilters: Filter[]; // empty until RLS (P2 Pro)
}

interface Connector {
  type: 'postgres' | 'mysql' | 'excel' | 'gsheet';
  capabilities: { supportsRawSql: boolean; supportsWrite: false };
  testConnection(ds: LoadedDatasource): Promise<void>;
  discoverSchema(ds: LoadedDatasource): Promise<TableSchema[]>;
  query(ds: LoadedDatasource, spec: QuerySpec, ctx: SecurityContext): Promise<QueryResult>;
  runSql?(ds: LoadedDatasource, sql: string, values: unknown[], ctx: SecurityContext): Promise<QueryResult>;
}
```

`DatasourcesService` selects a connector from a registry and holds no source-specific logic. The existing Postgres code moves behind this interface. `runSql` exists only on `postgres` and `mysql`. `CollegeService` keeps working and passes a `SecurityContext` built from the logged-in user.

### QuerySpec

```ts
interface QuerySpec {
  table: string;
  columns?: string[];
  filters?: Filter[]; // { column, op, value }
  groupBy?: string[];
  aggregates?: { fn: 'count' | 'sum' | 'avg' | 'min' | 'max'; column?: string; as: string }[];
  orderBy?: { column: string; dir: 'asc' | 'desc' }[];
  limit?: number;
}
```

Filter operators: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `contains`, `isNull`.

`compileQuery(spec, schema, dialect, ctx)` is a pure function that returns `{ text, values }`.

- Every table and column name must exist in the discovered schema. Anything else is rejected before SQL is built.
- Identifiers are quoted for the dialect. All values are bound parameters.
- `ctx.rowFilters` are ANDed in unconditionally, so a caller cannot remove them.
- `limit` is capped at 10,000 rows. Results above that are marked `truncated`.

### Imported data

New Prisma model:

```prisma
model DataTable {
  id           String   @id @default(cuid())
  datasourceId String   @map("datasource_id")
  name         String
  storageName  String   @map("storage_name") // paarvix_data.t_<cuid>
  columns      Json
  rowCount     Int      @map("row_count")
  syncedAt     DateTime @map("synced_at")
  datasource   Datasource @relation(fields: [datasourceId], references: [id], onDelete: Cascade)

  @@unique([datasourceId, name])
  @@map("data_tables")
}
```

`storageName` is generated by Paarvix and never contains user text. Prisma manages only `public`, so `prisma db push --accept-data-loss` at startup must leave `paarvix_data` alone. The implementation must confirm this by restarting with imported data present.

**Import pipeline** (shared by Excel and Sheets):

1. Read the workbook with the `exceljs` streaming reader. Each non-empty worksheet is one table.
2. The first non-empty row is the header. Blank headers become `column_1` and so on. Duplicates get a numeric suffix.
3. Infer each column type from all values: `number`, `date`, `boolean`, or `text`. A column with mixed values is `text`. Formula cells use their stored result. `₹` and Indian digit grouping such as `1,25,000` parse as numbers. `DD-MM-YYYY` and `DD/MM/YYYY` parse as dates.
4. Load into a new table, then swap it in and update `DataTable` in one transaction. A failed import leaves the previous data untouched.
5. Deleting a data source drops its imported tables.

**Limits:** `.xlsx` only, confirmed by ZIP signature as well as extension. 50 MB per file (already enforced in `main.ts`), 50 sheets, 500 columns, 1,000,000 rows per sheet. Macros are never run or stored. The original upload is discarded after import.

### Google Sheets

The admin pastes a sheet link. Paarvix extracts the spreadsheet ID and validates it against `^[a-zA-Z0-9_-]+$`.

- **Public link:** download the `.xlsx` export from `docs.google.com`.
- **Private sheet:** the admin shares it with a service account and pastes the JSON key. Paarvix signs an RS256 token with Node `crypto`, and downloads the `.xlsx` through the Drive export endpoint with read-only scope.

Both feed the import pipeline. Requests go only to fixed Google hosts, built from the validated ID, so they cannot be pointed at internal addresses. The key is stored with `encryptSecret` and never returned by the API.

Google limits exports to about 10 MB. A larger sheet fails with a clear message.

**Sync:** a Sync button plus an optional interval of 15 minutes or more, default off, run by an in-process timer. Only one sync runs per source. A failed sync keeps the old data and records `lastSyncError` in `Datasource.config`, shown in the UI. Sources display "last synced" time.

### MySQL and MariaDB

Uses `mysql2` with `multipleStatements: false`, a new connection per query, TLS option, and the same limits as Postgres: 30 seconds and 10,000 rows.

- `START TRANSACTION READ ONLY`, then `ROLLBACK`.
- Timeout uses `max_execution_time` on MySQL and `max_statement_time` on MariaDB, chosen from the server version.
- `assertReadOnlySql` is shared, and queries are wrapped in the same limited outer `SELECT`.
- Docs require a read-only database user, because the regex is only a first filter.

`discoverSchema` reads `information_schema`, skipping system schemas, for both MySQL and Postgres.

## API

All routes use `JwtAuthGuard`. Admin-only actions keep the current role checks.

| Route | Role | Purpose |
|---|---|---|
| `POST /datasources` | Admin | Create `mysql`, `gsheet` or `postgres` |
| `POST /datasources/upload` | Admin | Create `excel` from a multipart file |
| `POST /datasources/:id/upload` | Admin | Replace an `excel` source's data |
| `POST /datasources/:id/sync` | Admin | Sync a `gsheet` source |
| `GET /datasources/:id/schema` | Admin, Editor | Tables and columns |
| `POST /datasources/:id/data` | Admin, Editor | Run a `QuerySpec` |
| `POST /datasources/:id/query` | Admin, Editor | Raw SQL. Returns 400 for `excel` and `gsheet` |

Viewers get no direct data routes in stage 1. They receive data through dashboards in stage 2.

## Web UI

Extend `datasources.component.ts`: a source type chooser, an Excel upload with progress, a Sheet link form, a MySQL form, a schema view with a 50-row preview, and Sync and last-synced status. New strings use the installed `@ngx-translate` setup with `en` and `ta` entries. The screen must work at phone width.

## Errors

Users see plain messages such as "This file has no data", "Paarvix cannot read this sheet: share it or make it public", or "Could not connect to the database". Server logs hold details. Logs and error responses never include passwords, keys or row data.

## Verification

- **Unit tests:** `compileQuery` covers unknown columns, injection attempts in names and values, `rowFilters` always applied, and limit caps. Also read-only rejection of non-SELECT SQL, and type inference for Indian numbers and dates.
- **Manual run:** compile and start the API and web app, then exercise a generated `.xlsx`, a test Sheet, and a local MySQL. No real student or company data is used.
- **REA and Chrome:** screenshots and page checks of our own Data Sources screen, and bundle size against the 400 KB budget. Never used on Grafana.
- **Docs:** `CHANGELOG.md`, user guides in `docs/guide/` (getting started, connecting data, sectors and customising), `docs/roadmap.md`, and an ADR in `docs/adr/` for the import design. `CLAUDE.md` gains the ERP pack in stage 3.

## Out of scope

Dashboard builder, panels, ERP templates, alerts, CSV and `.xls`, joins across sources, DuckDB, RLS rules, multi-tenancy, Tally, Zoho and ERPNext.

## Known risk, handled separately

`docker/Dockerfile.api` and `install.sh` run `prisma db push --accept-data-loss` on every start. A future schema change could silently delete columns in a real company's install. This should move to `prisma migrate deploy` before the first paying client, as its own task.
